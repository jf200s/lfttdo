## 1. R189① 的 Rust 探针：`src-tauri/examples/image_prep_probe.rs`

brief 原判据「DevTools 里确认 base64 长度 ≤5MB」在这条栈上看不见东西（R189），所以字节数只能在
Rust 侧量。探针是零 key、零端点依赖的纯本地路径，属于本任务的「代码身体」：

```bash
cd src-tauri && cargo run --release --example image_prep_probe -- <图片路径> …
```

它打印三件互相独立的事实：**头部声明的格式与尺寸**（`image_dimensions`，只看 metadata）、
**`normalize_image` 返回的 mime 与 base64 字节数**、以及**把那段 base64 解回图片再读一次的宽高**。
第三件是刻意的：缩放后尺寸如果由探针自己复算，被测对象就被换成了探针自己。

### 1.1 字节表（release，2026-10-23 12:12 实测）

「解回尺寸」那一列把返回的 base64 解码后**重新读一遍尺寸**，并顺带报出编码后字节与
**输出里还带着的 EXIF 方向标签**（后者是 §4 的判据，那里的说明写了它为什么不是多余的一列）。

| 输入 | 原字节 | 头部声明 | 结果 mime | base64 字节 | 解回尺寸 | 编码后字节 | 输出方向标签 | 耗时 |

| `tall-shot.png`（Chrome headless 截的真长页面） | 96 886 | Png 1000×2600 | **png** | 113 352 | **603×1568** | 85 012 | NoTransforms | 25 ms |

### 1.2 延迟必须用 release 量（本轮踩到的）

同一份探针、同一批夹具，`dev` profile 的数字是 `big-alpha` **3581 ms**、`noise-3600` **3422 ms**、
`phone-exif6` **1305 ms**；release 是 289 / 249 / 71 ms。**差 12–13 倍**。
⇒ 任何「归一化要多久」的结论只能在 release 上取；`cargo run --example`（不带 `--release`）会给出

`base64 字节 / 编码后字节` 恒为 1.3334（4/3 加换行对齐），与 `base64_len()` 的算式一致。

### 2.3 一张图会把这条会话毒死（记录，不改代码）

同一条会话里再发**纯文本**（不带图）：

原因链：T20 的设计是最近 `KEEP_IMAGE_RECENT = 3` 张图**原样进请求**，而那张图已经在 history 里，

## 3. Step 2 超限指名（R188）—— 两条都在真窗口里跑了

### 3.1 字节闸：`图片太大`，而且它没被当成「认不出格式」

把 **41 000 000 字节的纯随机字节**改名成 `oversize-fake.png` 喂进 `[data-testid="file-input"]`，
界面第一行（原文照抄，`[data-testid="image-error"]`）：

```
oversize-fake.png：图片太大（当前 41000000 字节），请先裁剪或缩小后再发送
```

同时 `document.querySelectorAll(".image-thumb").length === 0` ⇒ **图没有进 pending，也就没被发送**
（R188 要的「pending 保留」在这里是「pending 根本没长出来」，因为这一次连归一化都没通过）。

这条顺带把**闸门顺序**证死了，用了两个独立事实：① 探针里这一行 **0 ms** 返回；
② 同一个文件的头部读取器自己报「认不出 / 读不出」（它根本不是图片）。
⇒ 报出来的却是「图片太大（当前 41000000 字节）」而不是「图片无法识别为图片」，
`bytes.len() > MAX_INPUT_BYTES` 必然走在 `with_guessed_format()` 之前（R185 要的正是这一句）。

### 3.2 37 MB 的真噪声 png：缩放救回来了

`noise-3600.png`（3600×3600、38 926 642 字节，刻意留在字节闸下 1 MB 的余量）喂进同一个入口：
**没有错误行**，缩略图长出来了，而且它的 `src` 头部是 `data:image/jpeg;base64,/9j/4AAQSkZJRgABA`
—— 界面自己显示的就是那张被缩放并重编码成 jpeg 的图。探针侧同一条输入：1568×1568、base64 3 550 824。
⇒ 「过得了字节闸、必须靠缩放才过得去」这一支**不是报错**（R188 的后半句）。
「图真的发出去了、模型真的看见了」那半句在下面 §7。

### 3.3 `TooLargeAfterCompression` 今天从界面不可达（R184 的算术 + 本轮两个落点）

本轮两个「必须降质」的输入最后落在 **3 953 132** 与 **3 550 824** 字节，都在线内；
png 回落的第一级 q=85 在 1568² 噪声上是 5.18 MB（**R184 的实测表**，本轮没有重测这一格），
刚好超 ⇒ 阶梯走到第二级 q=75 就回来了。界面能碰到的超限路径只有 §3.1 那一条。
「图片降质到最低后仍超过 5MB」这句话按 R184④ 记为**安全带**：它存在是为了让谁也别把
`MAX_EDGE_PX` 或阶梯改窄时静默放大载荷，而不是为了被用户读到。

## 4. EXIF 方向（R182）—— 机器这一半过了，人工那一半没做

夹具（`make_fixtures.py`）：先画一张**正立**的 1600×2400 场景（顶 `UP`、底 `DOWN`、左侧一条竖色带、
左上角一块绿），把它逆时针转 90° 存成 2400×1600 的像素，再打 `Orientation=6`（=「显示时顺时针转 90°」）。
于是「还原正确」的唯一形态是输出重新变成竖的。

实测：`phone-exif6.jpg` 头部声明 **2400×1600**，`normalize_image` 之后解回 **1045×1568**，
而输出字节里的方向标签是 **`NoTransforms`**。

**为什么要多读那一列标签**：「先烘焙方向再缩放」和「先缩放再烘焙方向」得到的宽高**一模一样**
（都按长边 2400 缩，1568/2400=0.653 ⇒ 1045×1568），所以宽高只能证明「方向被处理过」，
不能证明它已经进了像素。`NoTransforms` 才证明标签被用掉并且抹掉了 —— 这正是 R182 的配方
（jpeg 重编码会丢 EXIF，方向只能住在像素里）。内容那一半（模型是否读到 `UP` 在上方）在下面 §7。

**未执行（需人工在场）**：R192 写死这一条要用**手机直出的原图**，因为任何编辑器「另存为」都可能
已经把方向烧进像素或删掉标签，那会让验证自证通过。本机没有手机拍摄的原图，所以：
需要用户做的一件事 = 用相机拍一张带文字的竖照（不要经过任何编辑/微信传输），把原文件拖进界面，
问「图里的字是什么、正不正」。合成夹具这条**不能**替代它，只能替代 §4 里那两列数字。

## 7. 模型这一半：真窗口 + 本地 VL 端点（`qwen3-vl:8b`，2026-10-23 12:38–12:56）

现场：`qwen3-vl:8b` 5.77 GiB 拉完后，**`model` 是用设置面板自己改的**（打开面板 → 「模型名」输入框
走原生 value setter + `input` 事件 → 点「保存」），磁盘回读确认 `model = qwen3-vl:8b` 才开跑；
收尾再按同一入口改回磁盘当前值 `huihui_ai/qwen3-abliterated:14b-q4_K_M`。
**全程没重启进程** —— `ipc.rs:498` 每次 `send_message` 都重读设置，这一条顺带被验掉了。
延迟基线：拉完之后的第一次调用（直发 `/v1`，不经过应用）**18 969 ms**（把 5.77 GiB 装进显存的冷启动），

### 7.1 长截图（1000×2600 → 603×1568）：可读性判过

问「清单分了哪几类、每类的预算数字、最后合计多少」，答：

> 清单分为生鲜、日用、零食三类 生鲜：128元 日用：96元 零食：74元 合计：298元

原页数字是 128 / 96 / 74 / 合计 298 —— **四个数全对，三类全对**。
这张图长边被压到 1568（短边只剩 603），而表格里的小字仍然读得出来，所以 §1.1 那行
「96 886 → 113 352 base64、603×1568」不只是一串字节数：**缩放档位对一张文字长截图是可用的**。

### 7.2 EXIF 方向（§4 的内容那一半）

问「现在是正立还是侧躺、`UP`/`DOWN` 各在哪边、绿块在哪个角」，答：

> 图是正立的。 「UP」在图的上方，「DOWN」在图的下方。 绿色小方块在左上角。

夹具的正立画就是 `UP` 顶、`DOWN` 底、绿块左上（`make_fixtures.py` 里 `d.rectangle([120, 200, 200, 280])`），
**三处全中**。配合 §4 的 `NoTransforms`，R182 那条「decoder 先取方向 → `apply_orientation` → 再缩放再重编码」
在真链路上是成立的：方向进了像素，不是靠标签留给下游（下游也拿不到标签，jpeg 重编码把 EXIF 丢了）。
**但这一条仍不等于 R192 要的那次验证** —— 夹具是我合成的，不是手机直出原图，
`未执行（需人工在场）` 那一段（§4 末尾）一字不改地继续欠着。

### 7.3 透明 png 的两支（R190）

- **(a) 小透明 png（mime 仍是 png）—— 模型把透明区读成黑底**。原话：

  > 图中包含以下元素： 形状：绿色椭圆形（外层）、橙色正方形（内层）； 文字：底部灰色大写文字"TRANSPARENT BACKGROUND"； 背景：纯黑色。 （注：文字"TRANSPARENT BACKGROUND"是图像内文字，实际背景为黑色，非透明。）

  形状和文字都对（外圈绿椭圆、内块橙方、底部那行灰字）。**透明区被说成「纯黑色」**。
  这里要分清责任：`normalize_image` 这一支**没有**动 alpha —— 探针量到 mime `png`、尺寸 400×300 原样，
  alpha 字节是带着出门的；黑底发生在**端点侧的图像预处理**（把 RGBA 拍成 RGB 时按黑底合成，
  这是常见解码库的默认行为，本机这一条只观测到现象、没有读端点代码）。
  R190(a) 的判据原话是「透明区不产生『黑底/白底』的误读」，**按字面这一条没过**，
  但它不是归一化的缺陷，是「PNG 保 alpha 送到端点之后仍然会变成黑底」这个事实的记录。
  ⇒ 要不要在编码前自己把 alpha 合成到白底（那会改变 png 保 alpha 的设计），**列为待用户裁定**。
- **(b) 大透明 png（回落 jpeg）—— 能正常回答**。原话：

  > 这张图主要是由大量噪点组成的画面，颜色以浅灰色和深灰色为主，呈现类似电视雪花的干扰效果。画面中没有可辨认的物体或文字，整体是模糊的噪点分布。

  13 MB 的 RGBA 噪声缩到 1568×1568、回落 jpeg、base64 3 953 132，**端点收下了并且答得连贯**，
  「回落之后这条路径还能走通」判过。它说颜色是浅灰/深灰而不是彩色，符合一份逐字节随机噪声
  被大幅缩放后相邻像素平均掉的观感 —— 这一条不作判据，只作现场描述。

### 7.4 多帧 gif（R191 ③）

> 文字：FRAME ONE、color=red；背景颜色：红色。

三帧夹具的第 1 帧是红底 `FRAME ONE` + 白带 `color=red`，第 2 帧蓝、第 3 帧绿。

## 8. Step 3 历史图片降级实测：判据本身要先修一次，然后才是结论

### 8.1 先记下 R193 夹具的一个洞：**答案会自己溜进历史文本**

第一轮按 R193 照做：同一会话连贴 6 张、每张问「这张图里的数字是多少」。
六张**全答对**（7391 / 2048 / 5516 / 8270 / 1634 / 9052，每条气泡就是那个数），
这一步证明的是「模型认得出数字、贴图路径通」，**还没碰降级**。
接着按位置追问「第 1、2、3 张的数字是多少」：

> 7391 2048 5516

三个全对 —— 但这**不能**当成「降级没生效」的证据：这三张的数字早在第 1/2/3 轮的助手气泡里
以**纯文本**躺在历史里了，模型不用看图也能答对。原判据「贴一张写一个只属于那张的数字」
防住了「礼貌性编造」，却没防住「自己把答案念进历史」。换通道再试一次（问背景颜色，
数字之外的通道，历史里从没出现过颜色）：

> 第 1 张：浅米色 第 2 张：浅灰色 第 3 张：米白色 第 4 张：浅米色 第 5 张：淡紫色 第 6 张：浅灰色

真值是 米白/浅蓝/浅绿/浅黄/浅紫/浅灰 —— 只有第 5、6 张对得上，前四张是**编的**，
而且**一张都没说「看不到」**（R193 预言的礼貌性编造，在这里现形了）。
但这一轮仍不能当判据：淡色背景本来就是这条端点容易答错的通道，「答错」既可能来自降级、
也可能来自看不清，**分不开**。

### 8.2 决定性的那一轮：贴图轮**不让它开口**

改法只有一句：六轮（以及复跑的四轮）里的提问换成「只回一个字：收到」。
模型六次都只回「收到」，于是历史文本里**一个数字都没出现**，数字只能从图里来。
按位置追问（原话）：

> 第 1 张：8270 第 2 张：1634 第 3 张：9052 第 4 张：看不到 第 5 张：看不到 第 6 张：看不到

四张贴图的复跑（更干净的对照，原话）：

> 第1张：2048 第2张：5516 第3张：8270 第4张：看不到

读法：`digit-1..4` 分别是 7391 / 2048 / 5516 / 8270。模型手里**恰好三张**，
而且正是**第 2、3、4 张**（2048 / 5516 / 8270）—— 最老的那张 7391 它拿不到，
并且它**没有编**，直接说了「看不到」。六张贴图那一轮同理：它拿到的是 8270/1634/9052 = 第 4/5/6 张，
最老的三张全部不在手里。**`KEEP_IMAGE_RECENT = 3` 在真链路、真端点上成立**，
被换掉的那几张确实一个像素都没进请求。

**代价是可见的**：它把还在的三张**重新编号成了「第 1/2/3 张」**，
于是用户按位置问「第 1 张」时，答的是**第 2 张**的内容。
`窗口里图片的序号会随降级前移`——这条是这一节真正的产品结论，不是「模型看不看得清」。

### 8.3 降级占位符在 UI 上的实际形态：**没有形态**

四轮复跑结束时把整条会话的气泡全量读了一遍（原文）：

```
U imgs 1 | 只回一个字：收到     A imgs 0 | 收到
U imgs 1 | 只回一个字：收到     A imgs 0 | 收到
U imgs 1 | 只回一个字：收到     A imgs 0 | 收到
U imgs 1 | 只回一个字：收到     A imgs 0 | 收到
notices [] fatal None
```

**四个气泡各自还挂着一张 `<img>`，界面上一条降级痕迹都没有**。
原因在代码里也对得上：`degrade_old_images` 住在 `ContextBuilder::build()` 内部（`context.rs`），
改的是**发出去的那份请求**，落库的 `Image` 块和渲染它的气泡一个字节都不动，
`[图片已移除以节省上下文]` 这句**只在请求里存在，永远不进 DOM**。
⇒ R193 说的「用户看得见的那半句」目前是**零**。用户看到的仍然是 4 张缩略图，
而模型只收到 3 张 —— 差的那一张既没有标记、没有提示、也不能点开。
要不要在前端补一个「这张已不进上下文」的灰标，**列为待用户裁定**（它属于界面，不属于 T20 的算法）。

### 9.3 三条本轮踩到的方法账

1. **`DOM.setFileInputFiles` 之后「同一个 JS 任务里打字 + 点发送」会被吞**（2/2 复现，都发生在带图的那一轮）。
   拆成两次 CDP 调用（打字一次、点发送一次，中间 `sleep`）后 100% 发得出。
   这不是界面缺陷，理由写在代码里就对得上：`Composer.tsx:232-236` 是
   `streaming ? <button class="stop">停止</button> : <button type="submit" class="send">发送</button>` ——
   流式期间**根本没有「发送」这个按钮**，真实用户点不到「流式中提交」这条路，
   而合成事件的「设 value → 立刻 click」落在同一个 React 提交里，读的是上一帧的闭包。
   留下的真问题只有一个：`submit()` 早退时**零反馈**（不发消息、不清草稿、不出提示），
   而它只能被合成事件触发，所以记在这里，不记成缺陷。
2. **`Array.prototype.map(fn)` 会把 `(元素, 下标, 数组)` 三个参数都传给 `fn`**。
   一个只收一个参数的 `clean(s)` 直接 `.map(clean)` 会拿到 DOM 元素当 `s`，
   症状是「`(s || "").replace is not a function`」—— 看着像页面结构变了，其实是判据自己的 bug。
   写成 `.map((b) => clean(b.textContent))` 才对。
3. **Ollama 的 `-partial` 文件一开始就预分配成最终大小**，`du`/`ls` 看到的字节数**不是进度**。
   12:22 时那个 1 162 568 672 的文件看着「下完了」，其实 `completed` 只到 1 143 091 360。
   要进度只能问 `/api/pull` 自己（再开一条流读 `status` 行，它会并进在跑的那次拉取，不重下）。
