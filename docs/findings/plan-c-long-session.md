## §4 判决：备注行是永久预算 —— `stuck_rounds > 0`

**结论：小预算那一档（A：66 / 100 轮，C：38 / 60 轮）病态可测；大预算那一档（B：0 轮）没有。**

三条事实全部实测过（不是读码推测）：

1. 备注**单调累积**：A 100 轮压了 22 次 ⇒ 库里 22 条备注，一条都没被并进后续摘要
   （`conv` 与「一轮」的定义排除 `Role::System`，`db.rs:1228` 那条测试明文钉着
   `notes == [NOTE_A, NOTE_B]`）。⇒ 计划 Step 7 那句「带前缀好让第二次压缩把它一起并进新摘要」
   **在当前形状下不成立**。
2. 备注**吃预算**：A 的 22 条 = 396 token = usable 的 **11%**（≈ 1.5 轮原话的单价 268 token）。
3. 备注**推动压缩、自己永不被压缩**：它进 `compaction_plan` 的 `raw`（触发线），
   又进 `build()` 的 `head`（滑窗裁不到）⇒ 触发线被**提前跨过**，而批量下限
   （`MIN_COMPACT_TURNS = 4` 与 `.min(turns - keep_turns)`）把它挡在门外。

**越线时刻的形状**（把实测常数代进 `compaction_plan` 自己的算式，全部相加性口径）：
`est = 69 + 18·n_notes + 268·turns`，`line = 3046`，而压缩最早能触发是 `turns ≥ K + 4 = 14`。

- `n_notes = 0` 时越线发生在 `turns = 12` ⇒ 每个周期只有 **2 轮**处于「已越线、压缩拒绝」。
  （⇒ A 的头两次 stuck（第 12、13 轮）就是这一档，**与备注无关**，是 line 与批量下限之间的结构性缺口。）
- `n_notes` 每 +1 就把越线时刻提前 `18/268 ≈ 0.067 轮`；**由实测常数推出**：`n_notes ≥ 17` 时
  刚压完那一刻（`turns = K = 10`，est = 69 + 2680 + 18n）就已经越线 ⇒ stuck 带占满
  **整个周期**（10..13 全 4 轮），压缩每轮都在被拒绝，改由滑窗从**最老的原话**静默丢字。
  A 实测到 22 条 > 17 ⇒ 与观测一致（66 轮 stuck、平均每周期 3 轮）。
  ⚠ `n_notes ≥ 17` 这个数是**推出的，未实测**（要跑它得改 `summary_chars` 或 K，那属于本片禁止的范围改动）。
- **没走到「永久返回 None」那个最坏形状**：100 轮里压缩仍然触发了 22 次（因为 4 轮一批
  恰好等于下限），所以本片**观测不到**「压缩永久返回 None 且无任何恢复路径」，
  只观测到「每周期 3–4 轮靠滑窗兜底」。这一条要在报告里如实分开：**阈值前移是真的，
  永久卡死没跑到**。

**要用户拍的决策（二选一，代价各一条）**：

| 选项 | 代价 |
|---|---|
| ① 把旧备注并进新摘要 | 要允许摘要吃 `Role::System` 行 ⇒ 动「一轮」的口径与 `conv` 的划分；**「吃掉用户原话」那条红线要整轮重测**（`db.rs` 的 `the_second_compaction_does_not_count_the_note_as_a_conversation_row` 是它的钉子，会先红） |
| ② 备注条数设上限（超出即丢最早那条） | 实现只动 `compact_session` 附近；**丢掉的是最早那段的要点**，而且界面得让用户知道丢了（今天 `Role::System` 行在重放里完全不可见 ⇒ 用户看不出来丢了几轮） |

**留给「将来改 K 或改阈值」的参照基线**（本片实测）：
`K=10 / threshold=0.85 / usable=3584 / 268 token 每轮 / 18 token 每条备注` 时 ——
备注入库 22 条 = 396 token = 11% 预算，stuck 带 = 66/100 轮，静默丢字 44 行。
任何把 `keep_turns` 调小、把 `compact_threshold` 调高、或把 `summary_chars` 调大的改动，
都会同时移动这三条线，改之前应先对齐这组数字。
